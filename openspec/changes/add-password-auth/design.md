# Design

## Context

Причины и состав изменения — в `proposal.md`, требования — в `specs/`. Что важно
для реализации:

- Всё внутри стека опирается на `users.id` (UUID) и claim `sub`, а не на Google.
  Google-специфичное — только `users.google_sub NOT NULL UNIQUE`, `picture`, три
  спеки входа и кнопки в клиентах.
- Сессия (access JWT + refresh в Redis, `device-sessions`) выпускается одним
  кодом независимо от способа входа; новый способ входа должен прийти в этот же код.
- В `redis_client` реализованы только `SET..EX`, `EXISTS`, `DEL` (и `GETDEL` для
  refresh); для счётчиков попыток нужны ещё `INCR` и `EXPIRE`.
- Приглашения в wallet-api идут по одноразовой ссылке (`/join/<token>`,
  `accept_invite` не сверяет email); email участника нужен только для показа в
  списке. Поэтому claim `email_verified` в токен **не добавляется**, wallet-api не
  меняется.
- TLS в стеке нет; его даёт отдельный change в wallet-infra, этот change лишь
  отказывает в приёме пароля по HTTP.

## Goals / Non-Goals

**Goals:**
- Вход и регистрация по email и паролю в google-auth, не меняя claim'ы токена и
  потребителей JWKS.
- Безопасное сосуществование с Google: без захвата аккаунта заранее (pre-hijacking).
- Переключение способов входа конфигурацией, без выката кода.

**Non-Goals:**
- Подтверждение email, письма, самостоятельный сброс пароля («забыл пароль») —
  отдельный change с SMTP.
- TLS и reverse proxy — change в wallet-infra.
- Формы в wallet-web и android-wallet, правки wallet-gateway — отдельные change.
- Двухфакторная аутентификация, парольные политики сложнее длины, список
  скомпрометированных паролей.
- Изменение ролей уже заведённых пользователей.

## Decisions

### D1. Учётные данные — отдельная таблица `user_passwords`

Миграция `000005`: таблица `user_passwords(user_id UUID PK REFERENCES users ON
DELETE CASCADE, salt BYTEA, iterations INT, hash BYTEA, updated_at TIMESTAMPTZ)`
и `ALTER TABLE users ALTER COLUMN google_sub DROP NOT NULL` (UNIQUE остаётся:
в Postgres несколько NULL в UNIQUE допустимы).

*Альтернатива:* колонки `password_hash` в `users`. Отвергнуто: хэши не должны
попадать в выборки `users` (список админа, `/auth/me`) по недосмотру, а отдельная
таблица удаляется целиком при Google-захвате и при удалении аккаунта каскадом.
Нужны права DML для роли сервиса — `ALTER DEFAULT PRIVILEGES` из `init-db.sh` их
уже выдаёт. Правка `000001`–`000004` не делается.

### D2. Хэш — PBKDF2-HMAC-SHA256 на OpenSSL, 600 000 итераций

Есть в OpenSSL (`PKCS5_PBKDF2_HMAC`), новых зависимостей нет — это важно,
потому что проект принципиально без пакетного менеджера. Число итераций хранится
в записи, при входе устаревшая запись пересчитывается.

*Альтернатива:* argon2id (современнее, устойчивее к GPU). Отвергнуто: нужна
сторонняя библиотека и сборка под Docker; можно перейти позже, не ломая данные,
если хранить в записи идентификатор алгоритма (добавить колонку `algo` — решить в
задаче 1.1, пока запись описывает только PBKDF2).

Цена: ~0,2–0,5 с на проверку на одном ядре. Вход блокирует рабочий поток
httplib, поэтому лимиты (D4) нужны ещё и как защита от перегрузки CPU.

### D3. Отказ входа без различий по времени

Для несуществующего email проверка идёт по фиктивной записи с теми же
параметрами. Единый текст `неверный email или пароль`. Регистрация отвечает
`202` всегда, чтобы нельзя было перебирать чужие почты. Сравнение хэшей —
`CRYPTO_memcmp`.

### D4. Лимиты попыток — счётчики в Redis, при недоступности Redis вход закрыт

Ключи `authfail:email:<sha256(email)>` и `authfail:ip:<ip>` с `INCR` +
`EXPIRE` на `AUTH_FAIL_WINDOW_SECS`. Окно фиксированное, а не скользящее — проще
и дешевле; допустимо при лимите 5 попыток. Нужно добавить `INCR`, `EXPIRE`
(и `TTL` для `Retry-After`) в `redis_client` — клиент свой, поверх сокетов.

IP берётся из `X-Forwarded-For`, который **перезаписывает** гейтвей; сам
google-auth наружу напрямую не публикуется, значит подделать заголовок можно
только изнутри контура.

*Альтернатива:* считать в памяти процесса. Отвергнуто: теряется при рестарте и не
работает при нескольких экземплярах.

### D5. Привязка Google к парольной записи — тот же приём, что у существующих пользователей

Google выигрывает у неподтверждённого пароль-аккаунта: `google_sub` привязывается,
`email_verified=true`, строка в `user_passwords` удаляется, сессии отзываются
(механизм `device-sessions`, «отозвать все»). Сейчас пользователь ищется по
`google_sub` (`repo::find_user_by_google_sub`, `repo::upsert_user`, обёртка
`get_or_create_user` в `auth.cpp`); привязка по email добавляется в этот же
путь: в браузерном входе — перед страницей «Аккаунт не найден», в мобильном —
перед созданием. Правка спеки `mobile-sign-in` не нужна: поведение описано в
`password-auth`, а в задаче 3.2 проверяется, что оба пути его выполняют.

*Альтернатива:* предлагать выбор («объединить?»). Отвергнуто: у владельца почты в
этот момент нет способа убедиться, что аккаунт заведён не им, а подтверждённый
Google email — единственный надёжный источник.

Обратное направление — Google-аккаунт, на чей email регистрируется пароль —
отказано молча (D3): `POST /auth/register` ничего не меняет. Пользователь Google
может задать пароль через `POST /auth/password`, будучи залогиненным.

### D6. Проверка схемы — по `X-Forwarded-Proto`

Приём пароля по HTTP закрыт по умолчанию. Заголовок проставляется reverse proxy
и перезаписывается им же; логика та же, что у `X-Forwarded-Host` (см.
`browser-sign-in`). `ALLOW_INSECURE_AUTH=true` — явное согласие владельца
на ненадёжный режим (LAN без TLS); при запуске пишется предупреждение.

### D7. Один выпуск сессии

`POST /auth/login` вызывает тот же код выпуска, что `/auth/google/callback` и
`/auth/google/mobile`. Разветвление web/Android — по полю `platform`, как в
`mobile-sign-in` (нет `platform` или `web` → cookie; иначе → тело).

## Risks / Trade-offs

- **Пароль по HTTP в LAN** (пока нет TLS) → отказ по умолчанию, `ALLOW_INSECURE_AUTH`
  включается осознанно, предупреждение при запуске, предупреждение в UI клиентов
  при `http://`.
- **Неподтверждённый email в списке участников кошелька** (любой может
  зарегистрироваться на чужой адрес и, получив приглашение по ссылке,
  выглядеть как этот адрес) → риск принят: приглашение — одноразовая ссылка, её
  получает тот, кому её отправили; закрывается в change с SMTP показом статуса
  «email не подтверждён». Нужно сообщить владельцам кошельков в документации.
- **Нагрузка на CPU от PBKDF2** → лимиты по IP и email, число итераций настраивается
  (`PASSWORD_PBKDF2_ITERATIONS`, по умолчанию 600 000).
- **Открытая регистрация без подтверждения → спам аккаунтов** (в wallet-api
  кошелёк создаётся лениво при первом запросе, строк до этого нет) → лимит по IP
  на регистрацию, `REGISTRATION=closed` как выключатель, метрики `password_auth_total`.
- **Захват email админа**: `email_verified=false` → роль всегда `user`, поэтому
  email из `ADMIN_EMAILS` через пароль админом не станет.
- **Redis недоступен → вход по паролю невозможен** (вход через Google живёт без
  счётчиков) → осознанно: лучше отказ, чем вход без лимитов.
- **Логи гейтвея и тела запросов** → не требуется доработки: `body_logging_forbidden`
  в гейтвее запрещает запись тел `/auth/*` даже при `LOG_BODIES=1`, значит пароли в
  журнал гейтвея не попадут. google-auth сам тела не пишет (см. журнал и метрики в спеке).
- **Подделка `X-Forwarded-Proto` и `X-Forwarded-For`** (гейтвей сейчас пересылает все
  заголовки клиента как есть) → change wallet-gateway: заголовки перезаписываются,
  если запрос не пришёл от доверенного прокси.

## Migration Plan

Порядок выкатки (claim'ы токена не меняются, потребителей JWKS трогать не нужно):

1. wallet-infra: TLS и `COOKIE_SECURE=true` (или осознанно `ALLOW_INSECURE_AUTH=true`).
2. wallet-gateway: перезапись `X-Forwarded-For`/`-Proto` (до включения пароля,
   иначе проверку схемы можно обойти заголовком клиента). Пути `/auth/*` уже проксируются.
3. google-auth: миграция `000005`, новая версия; значения по умолчанию
   `AUTH_METHODS=both`, `REGISTRATION=open` можно временно держать в `google`/`closed`,
   пока клиенты не обновлены.
4. wallet-web, затем android-wallet: формы входа и регистрации.
5. Включить `AUTH_METHODS=both`, затем при желании `REGISTRATION=open`.

Откат: `AUTH_METHODS=google` отключает ручки пароля без отката кода; откат
миграции `000005` возможен, только пока нет пользователей без `google_sub`
(`down` падает с понятной ошибкой, если такие есть).

## Open Questions

- Нужна ли колонка `algo` в `user_passwords` уже сейчас (см. D2) — решается в
  задаче 1.1, на спеки не влияет.
- Размер окна и пороги лимитов (5 / 30 за 15 минут) подбираются при проверке на
  живом стеке; значения настраиваются через переменные окружения.
