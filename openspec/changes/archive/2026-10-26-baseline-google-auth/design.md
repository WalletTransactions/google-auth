# Design: базовая спецификация google-auth

## Context

Мотивация — в `proposal.md`. Спецификации в `specs/` восстановлены по коду на
коммите `e274663` (main, 2026-10-26): `8a1417d` плюс правка `src/google.cpp`
(`rewrite_lan_ip_to_nip_io`: уже готовый nip.io-хост не переписывается второй
раз). Живая сверка — на тестовом контуре (`localhost:8091`, образ
`google-auth:0.1.0-rc.2` = `e0674b7`): от `e274663` он отличается только
`release.yml` и этой правкой, поэтому сценарий «Уже nip.io-хост» проверен
только по коду (юнит-теста у `rewrite_lan_ip_to_nip_io` нет — она в
анонимном namespace `google.cpp`).

Источники: `src/*.cpp|hpp`, `migrations/`, `CMakeLists.txt`, `Containerfile`,
`.env.example`, `.github/workflows/ci.yml`, `README.md`, `openapi.yaml`;
общие `util/jwt`, `util/jwt_claims`, `util/log`, `util/metrics` — из
`third_party/wallet-common/`. Окружение сверено с блоком `google-auth` в
`wallet-infra/compose.yaml`. На живом стеке при подготовке ничего не
проверялось — это задачи раздела 2.

При расхождении документа и кода источником базы считался **код**;
расхождения вынесены в «Наблюдения», а не исправлены.

## Goals / Non-Goals

**Goals:**
- Описать наблюдаемое поведение так, чтобы каждый сценарий проверялся
  юнит-тестом (`ctest`) или `curl` — через гейтвей для `/auth/*`, `/admin/*`
  или изнутри сети контура для `/internal/*`.
- Сохранить обоснование решений, которое живёт в комментариях и README.

**Non-Goals:**
- Поведение потребителей токена (гейтвей, wallet-api, wallet-report,
  wallet-ai) и клиентов (wallet-web, android-wallet, wallet-telegram).
- Устройство `util/` из wallet-common и внутренние ключи Redis — только то,
  что видно снаружи.
- Запуск без Docker (`scripts/windows`, `scripts/linux`) и `release.yml` —
  упоминаются, но не специфицируются.
- Исправление найденных расхождений и любое изменение поведения.

## Decisions

### D1. Семь capability по зонам ответственности
`browser-sign-in` и `mobile-sign-in` — два способа подтвердить личность у
Google; `session-tokens` — то, что сервис выдаёт после этого, и как это
проверяет; `device-sessions`, `telegram-linking`, `admin-users` — управление
сессиями и доступом поверх; `service-ops` — эксплуатация. Граница совпадает с
модулями `google.*`, `auth.*`, `devices.*`, `telegram.*`, `admin.*`, `docs.*`
+ `main.cpp`.

### D2. Регистрация — только по явному подтверждению (браузер)
Вход незнакомым Google-аккаунтом не создаёт пользователя молча: claim'ы ждут в
памяти до `POST /auth/google/confirm-signup`. В мобильном входе страницы нет —
тап «Войти через Google» в приложении уже явное действие, а HTML пришлось бы
показывать в WebView.

### D3. Свой JWT RS256 + JWKS вместо общего секрета
Потребители проверяют токен локально по `/.well-known/jwks.json`, без
похода в google-auth на каждый запрос и без `JWT_SECRET` в их конфиге (от
HS256 отказались при разъезде на сервисы). Цена — D4.

### D4. Отзыв действует только внутри google-auth
Хэш access-токена лежит в Redis с его TTL; logout, отзыв устройства и
принудительный выход удаляют его, и ручки google-auth перестают принимать
токен сразу. Гейтвей и сервисы в Redis не смотрят — у них токен живёт до
`exp` (15 мин). Мгновенный отзыв там потребовал бы сделать их stateful.

### D5. Refresh — одноразовый, хранится хэшем, связан с парным access
Обмен атомарно гасит старый токен (повтор украденной копии — `401`); детекта
кражи с отзывом цепочки нет. Запись refresh несёт хэш парного access-токена:
только эта связка позволяет отозвать ровно одну сессию, когда у старых
браузерных сессий ещё нет `device_id`. Redis для refresh-токенов — с AOF и
томом: потеря разлогинила бы всех на 30 дней.

### D6. Одна сессия на (пользователь, device_id) — инвариант выпуска
Схлопывание делается в единственной точке выпуска токенов, а не группировкой
на экране устройств, поэтому список не видит дублей. Браузер получает новый
`device_id` на каждый вход (стабильного id у браузера нет, а без `device_id`
wallet-api не пускает в `/sync/*`).

### D7. Токен бота — урезанный и без google-auth в aud
Бот не хранит сессии: на каждую команду берёт по связке токен на 5 минут с
`scope reports:read expense:write ai:use`. Без `google-auth` в `aud` украденным
токеном нельзя смотреть или отзывать устройства, выпускать код связывания,
удалять аккаунт. Отзыв доступа — удаление связки. `/internal/*` защищены
общим секретом; client assertion отложен (`org/docs/TODO_service_auth_tls.md`).

### D8. Роль — решение при создании, не профиль
`ADMIN_EMAILS`/`SUPPORT_EMAILS` влияют только на новых пользователей и только
при `email_verified`; дальше роль меняется правкой `users.role_id` в БД.

### D9. `/healthz` не трогает Postgres и Redis
Иначе сбой зависимости перезапускал бы живой процесс по healthcheck compose.

## Наблюдения

Расхождения документации и кода, а также неожиданное поведение. В этом
изменении не исправляются.

- **Р1.** README, «Telegram-бот» (`README.md:541–547`): «бот получает обычную
  пару токенов устройства… первый же `/auth/refresh` бота даёт 401». С шага 6
  `TODO_telegram_tokens.md` обмен возвращает только `{user_id, device_id}`,
  токен бот берёт на команду (`telegram.cpp`, `handle_exchange`, `handle_token`).
- **Р2.** README, «Telegram-бот» (`README.md:549`): «Прямой порт google-auth
  (`8080:8080` в `compose.yaml`)». В `wallet-infra/compose.yaml` порт
  google-auth на хост не публикуется — `/internal/*` доступен только из сети
  контура.
- **Р3.** README, «Кнопки-самотесты на странице успеха» и комментарий
  `README.md:249`: страницы успеха нет — callback отвечает редиректом на `/`
  (`google.cpp:290`, `handle_verified_claims`).
- **Р4.** README, «Удаление аккаунта» (`README.md:296`): «единственный внешний
  ключ, ссылающийся на `users`, это её же `role_id`». Есть
  `telegram_links.user_id … ON DELETE CASCADE` (`migrations/000004`).
- **Р5.** README, «Структура» (`README.md:190`): `db` — «одно соединение +
  мьютекс». Сейчас пул `DATABASE_POOL_SIZE` (по умолчанию 8, `main.cpp:272`).
- **Р6.** README (`README.md:8, 70–73, 187, 208`) упоминает wallet-bff как
  потребителя JWKS и цель ссылки «На главную»; такого сервиса в стеке нет.
- **Р7.** `verify_schema` проверяет только `roles` и `users`
  (`db.cpp:56`): без миграции `000004` сервис стартует, а ручки связывания
  Telegram падают `500`. Подтверждено на отдельном контейнере (сверка 2.7):
  `POST /internal/telegram/token` — `500` с пустым телом.
- **Р8.** `openapi.yaml` не описывает `GET /metrics` как путь (упомянут только
  в описании, `openapi.yaml:104`).
- **Р9.** Комментарий `docs.cpp:116`: «все API-пути сервиса начинаются с
  `/api/` или `/sync/`» — у google-auth это `/auth/*`, `/admin/*`,
  `/internal/*`.
- **Р10.** HTML-страницы (`pages.cpp:49–50` и др.) ссылаются на `/style.css` и
  `/favicon.svg`, которых сервис не отдаёт: стили есть только через гейтвей
  (их отдаёт wallet-web), на прямом `:8080` — `404` и страница без стилей.
- **Р11.** Выданные nonce, PKCE-записи и отложенные регистрации живут в памяти
  без срока и без предела (`app_state.hpp:95–112`), а `POST /auth/nonce` и
  `GET /auth/google` анонимны. Поток таких запросов растит память процесса
  при `mem_limit: 64m` в compose.
- **Р12.** JWKS Google запрашивается на каждый вход без кэша
  (`google.cpp:499`): лишняя задержка входа и зависимость от
  `www.googleapis.com` на каждом входе. Живой вход на тест-контуре (сверка
  2.1): callback — 795 мс.
- **Р13.** Все отказы браузерного входа отдаются со статусом `200`
  (`pages.cpp:75`, вызовы с `google.cpp:184`): по метрикам `http_requests_total` неудачный вход не
  отличить от удачного показа страницы.
- **Р14.** Комментарий `telegram.cpp:295`: «гасит сессию устройства бота — ту,
  что пока хранит бот (до шага 6)» — шаг 6 выполнен; отзыв остался только для
  сессий, выпущенных до него.
- **Р15.** `created_at`/`last_login_at` в `GET /admin/users` — текст
  Postgres как есть (`2026-10-26 17:40:10.464176+00`, `repo.cpp:21–22`,
  `row_to_user`), а `created_at` в `GET /auth/telegram/links` — ISO 8601
  (`2026-10-26T17:42:28Z`): два формата времени в одном API (сверка 2.6).

## Risks / Trade-offs

- [Спецификация фиксирует и неудачное поведение (Р7, Р11–Р13)] → это база, не
  цель; исправления — отдельными changes с дельтой к этим спекам.
- [Сценарии с Google (неверный `id_token`, nonce) нельзя прогнать на рабочем
  стеке без настоящего входа] → проверять юнит-тестами там, где они есть, и
  ручным входом в браузере и с телефона; остальное отмечать как проверенное по
  коду.
- [Сверка пишет в живые данные (вход, отзыв сессий, связки Telegram,
  удаление аккаунта)] → делать на тестовом контуре и на отдельном тестовом
  Google-аккаунте; в задаче называть, какие данные затронуты.

## Migration Plan

Не требуется: код не меняется. После сверки change архивируется
(`/opsx:archive`), спецификации переезжают в `openspec/specs/`.
