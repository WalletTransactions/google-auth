# google-auth (C++)

Auth-сервис проекта: "Sign in with Google" (OAuth 2.0 Authorization Code +
PKCE), криптографическая проверка `id_token` по JWKS Google и своя сессия
(JWT) поверх неё. CRUD кошельков раньше жил тут же как пример защищённого
REST — теперь выделен в отдельный сервис со своей БД, см.
[wallet-api](https://github.com/WalletTransactions/wallet-api); этот сервис он использует только для проверки
токена (JWKS), как и wallet-bff/wallet-gateway.

Полное описание HTTP API (пути, тела запросов/ответов, коды ошибок) —
[`openapi.yaml`](openapi.yaml). Сервис отдаёт его и сам: `GET /openapi.yaml`
— файл как есть, `GET /docs` — Swagger UI поверх него (вендоренный
статический бандл, `third_party/swagger-ui/`, без CDN — см. его README).

Верификация настоящая: сервер проверяет подпись `id_token` (RS256) по
публичным ключам Google, а также `issuer`, `audience` и срок действия — а не
просто доверяет ответу без проверки.

## Зависимости

Минимум внешних зависимостей, специально без пакетного менеджера (vcpkg/Conan
не требуются):

- **CMake** ≥ 3.16 и компилятор с поддержкой C++17 (MSVC 2019+, GCC 9+, Clang 10+).
- **OpenSSL** (dev-пакет с заголовками).
- **PostgreSQL** (клиентская библиотека `libpq` + заголовки — под `users`, см. `db.hpp`/`repo.hpp`). Сам сервер Postgres, разумеется, тоже нужен, но не обязательно на этой же машине — только строка подключения в `DATABASE_URL`.
- **Redis** — сам сервер (не обязательно на этой же машине, см. `REDIS_HOST`/`REDIS_PORT` ниже), под активные access-токены (см. `redis_client.hpp`/`repo.hpp` и «Персистентность» ниже). Клиентской библиотеки НЕ требуется — протокол (RESP) реализован вручную поверх голых сокетов в `src/redis_client.cpp` (три нужные команды — `SET..EX`/`EXISTS`/`DEL` — не повод тащить hiredis отдельной зависимостью, тем более без внятного пути её установки под Windows-сборку вне Docker).
- `third_party/httplib.h` ([cpp-httplib](https://github.com/yhirose/cpp-httplib) v0.53.1) и `third_party/nlohmann/json.hpp` ([nlohmann/json](https://github.com/nlohmann/json) v3.12.0) — уже лежат в репозитории как одиночные заголовочные файлы, ничего дополнительно ставить не нужно.

Никакого vcpkg/Conan — только `find_package()` на системные библиотеки (OpenSSL, PostgreSQL). JWT, base64url, SHA-256/HMAC/RSA-verify, UUID, клиент Redis — реализованы вручную поверх OpenSSL/сокетов и nlohmann::json (см. `src/util/`, `src/redis_client.*`), чтобы не тащить отдельные библиотеки ради небольшого объёма кода.

## 1. Получить Client ID / Client Secret в Google Cloud Console

1. Откройте https://console.cloud.google.com/ и создайте проект (или выберите существующий).
2. **APIs & Services → OAuth consent screen**:
   - User type: External (или Internal для Google Workspace-организации).
   - Заполните название приложения, email поддержки.
   - Scopes: `openid`, `email`, `profile`.
   - Test users: пока приложение в статусе "Testing", добавьте свой Google-аккаунт.
3. **APIs & Services → Credentials → Create Credentials → OAuth client ID**:
   - Application type: **Web application**.
   - Authorized redirect URIs: `http://localhost:8090/auth/google/callback` — **порт гейтвея (8090), не этого сервиса** (должно точно совпадать с `REDIRECT_URL` из `.env`, см. ниже "Через гейтвей, не напрямую"). Пока переходите с одного значения на другое — можно держать в списке сразу оба URI, Google это разрешает. Если нужен одновременный вход и с этой машины, и с LAN-устройств — добавьте сюда же ещё один URI и см. ниже "Вход и с localhost, и по LAN одновременно".
4. Скопируйте **Client ID** и **Client secret**.

### Через гейтвей, не напрямую

`REDIRECT_URL` указывает на [wallet-gateway](https://github.com/WalletTransactions/wallet-gateway) (`:8090`), а
не на этот сервис (`:8080`) — так Google возвращает браузер на гейтвей,
который прозрачно проксирует `GET /auth/google/callback` сюда (префикс
`/auth/*` у гейтвея не под JWT-гейтом, см. его README) и отдаёт ответ
браузеру как есть. Разница на первый взгляд незаметна (код обмена/верификации
здесь не меняется вообще — `redirect_uri` для Google — просто строка, ему
всё равно, кто в итоге ответит по этому адресу), но она важна для браузера:
раз запрос уходил на `:8090`, success-страница получает origin `:8090`, а не
`:8080` — значит её `<a href="/">На главную</a>` сам ведёт на wallet-bff
(через тот же гейтвей), а `fetch('/api/wallets')` на success-странице сам
попадает на wallet-api — оба без ручного "откройте адрес гейтвея" и без CORS
(см. README wallet-bff, там раньше было наоборот и подробно расписано, что
именно это ломало).

Если открыть этот сервис прямо на `:8080` (в обход гейтвея, например
курлом) — `/auth/google` и `/auth/google/callback` всё равно работают сами
по себе (это не проверка адреса, откуда пришёл запрос), просто вернувшаяся
success-страница получит origin `:8080`, и её кнопки/ссылка на главную
поведут не туда, где ждёте (см. пример в самой странице).

### Вход и с localhost, и по LAN одновременно

`REDIRECT_URL` — одно статическое значение, а Google требует, чтобы
`redirect_uri` в запросе кода и в обмене кода на токен совпадали буквально
(RFC 6749 §4.1.3). Значит одним статическим значением нельзя одновременно
обслуживать браузер на этой же машине (`localhost:8090`) и браузер на
устройстве в LAN (`http://<LAN-IP>:8090` — которому `localhost` не подходит,
он резолвится в само устройство, не в сервер).

Решение — `ALLOWED_REDIRECT_URIS` (см. `.env.example`): список
дополнительных redirect_uri через запятую. `google.cpp::resolve_redirect_uri`
смотрит на `X-Forwarded-Host` (его кладёт `wallet-gateway`, см. его
`main.cpp::proxy_request` — обычный `Host` до апстрима намеренно не
доходит) или, в обход гейтвея, на сам `Host`, и если получившийся
`http://<host>/auth/google/callback` есть в списке (`REDIRECT_URL` + все
`ALLOWED_REDIRECT_URIS`) — использует именно его для этого конкретного
входа; иначе — фолбэк на `REDIRECT_URL`. Выбранное значение живёт вместе с
PKCE-state (`AppState::pending`, `PendingLogin::redirect_uri`) до колбэка —
это и обеспечивает совпадение на обоих шагах.

**Каждое** значение (и `REDIRECT_URL`, и всё из `ALLOWED_REDIRECT_URIS`)
обязано быть заодно добавлено в Authorized redirect URIs того же Client ID в
Google Console (см. шаг 1 выше — можно держать сколько угодно записей на
одном клиенте) — сервер только выбирает МЕЖДУ уже разрешёнными Google
значениями, сам факт разрешения он не выдаёт: доверия голому `Host`
заголовка недостаточно (его шлёт клиент), а несовпадающее с Google
consent-списком значение Google всё равно отклонит на обмене кода.

Отдельная сложность LAN-адреса: Google не принимает голый IP в redirect_uri
("must use a domain that is a valid top private domain") — обходной путь,
который используется в этом проекте: wildcard DNS вида `nip.io`/`sslip.io`
(`http://192.168.1.105.nip.io:8090/auth/google/callback` резолвится ровно в
`192.168.1.105`, но для Google выглядит обычным доменом с валидным TLD).

Набирать этот длинный nip.io-адрес в браузере руками не нужно:
`resolve_redirect_uri` сам переписывает голый Host из подсети `192.168.*`
(`192.168.1.105:8090`) в его nip.io-эквивалент (`192.168.1.105.nip.io:8090`)
ДО сверки со списком выше — обычный `http://192.168.1.105:8090` тоже
работает, при условии что nip.io-версия всё равно зарегистрирована и в
`ALLOWED_REDIRECT_URIS`, и в Google Console (сама сверка со списком не
ослабляется). Другие подсети (`10.*`, `172.16-31.*`) не переписываются —
под них нужен свой такой же nip.io-адрес в `ALLOWED_REDIRECT_URIS`, без
автоматической подмены Host.

## 2. Настроить проект

```bash
cp .env.example .env
```

Впишите `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, сгенерируйте RSA-ключ
для подписи СВОИХ access-токенов (не путать с Google client secret) —

```bash
openssl genrsa -out jwt_signing_key.pem 2048
```

— и укажите путь к нему в `JWT_RSA_PRIVATE_KEY_PATH`, а также `DATABASE_URL`
(строка подключения к Postgres, `postgresql://user:password@host:5432/dbname`
— база и роль должны уже существовать, таблицы сервис создаёт сам при
старте, см. «Персистентность» ниже) и `REDIS_HOST`/`REDIS_PORT` (адрес
Redis — сервер должен уже быть поднят, схему/структуру там заводить не
нужно, ключи появляются сами при логине):

```bash
# Linux/macOS
openssl rand -hex 32
# Windows PowerShell
[Convert]::ToHexString((1..32 | ForEach-Object { Get-Random -Max 256 }))
```

## 3. Собрать и запустить

```bash
cmake -S . -B build
cmake --build build --config Release
```

Если CMake не находит PostgreSQL сам (типичная ситуация на Windows —
официальный установщик не прописывается туда, где `find_package` ищет по

```

Бинарник: `build/google_auth` на Linux, `build/Release/google_auth.exe` на Windows.

**Важно:** запускайте бинарник из корня проекта — `.env` читается из текущей
рабочей директории (`./.env`), как и в большинстве dotenv-based приложений:

build\Release\google_auth.exe    # Windows (из корня проекта)
```

Сервер поднимется на `http://localhost:8080`. Откройте в браузере, нажмите
«Войти через Google», авторизуйтесь — увидите страницу с именем, email,
аватаром, статусом верификации и access-токеном для тестирования API.

## Структура

Один процесс, разбитый на модули с чёткой границей ответственности (1:1 с Rust-версией):

- `google.hpp/.cpp` — Sign in with Google: `GET /`, `GET /auth/google` (редирект с PKCE+CSRF `state`), `GET /auth/google/callback` (обмен `code` на токены, верификация `id_token` по JWKS). Только аутентификация — разовое подтверждение личности. Если такого `google_sub` ещё нет в `users` — не создаёт аккаунт молча, см. «Регистрация» ниже.
- `auth.hpp/.cpp` — своя сессия поверх этой аутентификации: заводит/находит внутреннего пользователя (`UserRecord`, `id` — свой UUID, не зависящий от формата Google-ID) и выпускает пару токенов — короткий access-JWT (RS256, по умолчанию 15 минут, cookie `session`, его хэш дополнительно кладётся в Redis с тем же TTL) и долгий opaque refresh-токен (по умолчанию 30 дней, хранится в Redis только как SHA-256-хэш, cookie `refresh_token` с `Path=/auth`). `auth::authenticate()` — то, чем остальные модули (и другие сервисы — wallet-api, wallet-bff, wallet-gateway) проверяют авторизацию запроса по access-токену; здесь, в самом google-auth, `authenticate()` вдобавок к подписи/`exp` проверяет присутствие токена в Redis (см. «Персистентность» ниже) — другие сервисы не трогают Google и не спрашивают auth-сервис на каждый запрос вообще, они сами качают публичный ключ с `GET /.well-known/jwks.json` (см. ниже) и проверяют подпись локально, без Redis. Сюда же — `POST /auth/refresh` (обменять refresh на новую пару, со сквозной ротацией через атомарный Redis `GETDEL` — старый сразу инвалидируется) и `POST /auth/logout` (отозвать и refresh-, и access-токен в Redis, очистить cookie).
- `admin.hpp/.cpp` — `GET /admin/users` (JSON-список всех пользователей — SPA сама рисует таблицу, см. `../wallet-web/site/app.js::renderAdmin()`) и `POST /admin/users/:id/logout` (принудительный отзыв всех токенов пользователя в Redis, см. «Принудительный logout» ниже) — оба только `Role::Admin`.
- `pages.hpp/.cpp` — HTML для браузерного флоу.
- `db.hpp/.cpp` — тонкая обёртка над `libpq` (одно соединение + мьютекс, см. комментарий в файле) + `verify_schema()` — проверяет, что схема уже накачена (создаёт её отдельная роль-мигратор, не этот сервис, см. «Персистентность» ниже). Теперь только под `users` — `refresh_tokens` здесь больше нет.
- `redis_client.hpp/.cpp` — тонкая обёртка над RESP поверх голых сокетов (одно соединение + мьютекс, тот же приём, что и `db.hpp`) — `SET..EX`/`EXISTS`/`DEL`/`GETDEL`, без внешней библиотеки.
- `repo.hpp/.cpp` — типизированный слой над SQL и над Redis: `auth.cpp`/`admin.cpp` работают с `UserRecord`, а не с сырыми запросами. И refresh-токены (`store/take/revoke_refresh_token`), и access-токены (`store/is_active/revoke_access_token`) — оба в Redis, спрятаны за узкими функциями — если бэкенд у любых из них сменится, меняется только этот файл.
- `util/` — base64url, SHA-256/RSA-SHA256-sign-и-verify (тонкая обёртка над OpenSSL, включая `RsaSigningKey` — RAII над приватным ключом, см. `crypto.hpp`), минимальный JWT (sign/verify RS256) поверх этого, UUID v4, url-encode, мини-dotenv, время (`now_epoch()`), логирование.

Пример защищённого JSON REST поверх выпущенного здесь access-токена — теперь
не тут, а в [wallet-api](https://github.com/WalletTransactions/wallet-api) (`POST`/`DELETE
/api/wallets`), см. его README.

### Проверка токенов другими сервисами (JWKS)

`GET /.well-known/jwks.json` — публичный (без авторизации) эндпоинт,
отдаёт публичную часть RSA-ключа, которым подписаны access-токены:

```json
{"keys": [{"kty": "RSA", "kid": "...", "use": "sig", "alg": "RS256", "n": "...", "e": "..."}]}
```

Так wallet-api, wallet-bff и wallet-gateway проверяют подпись сами — без
общего секрета в конфиге (раньше был `JWT_SECRET`, теперь только auth-сервис
знает приватный ключ) и без похода в auth на каждый запрос (JWKS кэшируется
у них в памяти, см. их `util/jwks.hpp`). Формат уже готов к ротации ключа —
`"keys"` это массив, можно отдавать сразу несколько с разными `kid`, старые
— пока не истекут все токены, подписанные ими.

### Регистрация: подтверждение вместо автосоздания

Если Google подтвердил личность, но такого `google_sub` ещё нет в `users`,
сервис **не создаёт аккаунт молча**. Вместо этого:

1. `handle_callback` откладывает уже провере́нные claims в `AppState::pending_signups`
   (в памяти, ключ — одноразовый `confirm_token`) и показывает страницу
   «Аккаунт не найден. Создать?» с email/именем/аватаром из Google.
2. Пользователь жмёт «Создать аккаунт» — обычная HTML-форма,
   `POST /auth/google/confirm-signup` с `token` — без JS, наш собственный
   `render()` не завязан на fetch.
3. Только тут реально появляется строка в `users` (`repo::upsert_user`), и
   выпускается пара токенов.

Уже существующий пользователь при повторном входе эту страницу не видит —
логинится сразу, как раньше. `pending_signups`, как и `pending` (PKCE), в
памяти процесса: рестарт сервера просто отправит недо-зарегистрированного
человека войти заново, ничего не теряется (аккаунт ещё не создан).

### Обновление сессии (`/auth/refresh`, `/auth/logout`)

Access-токен короткий (по умолчанию 15 минут — `ACCESS_TOKEN_TTL_SECS`), и
это осознанно: скомпрометированный токен быстро перестаёт работать. Чтобы не
логиниться через Google заново каждые 15 минут, есть refresh-токен (по
умолчанию 30 дней — `REFRESH_TOKEN_TTL_SECS`), непрозрачная случайная строка
в httpOnly cookie `refresh_token` (`Path=/auth` — браузер не шлёт её на
`/api/*`, только на сами `/auth/*`).

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/auth/refresh` | обменять refresh-токен на новую пару access+refresh |
| POST | `/auth/logout` | отозвать и refresh-, и access-токен (оба в Redis), очистить обе cookie |

```bash
# Браузер делает это через cookie автоматически (см. JS на странице успеха).
# Для API-клиента без cookie jar — передать refresh_token в теле:
curl -X POST -H "Content-Type: application/json" \
  -d "{\"refresh_token\":\"$REFRESH_TOKEN\"}" \
  http://localhost:8080/auth/refresh
# -> {"access_token": "...", "refresh_token": "...", "expires_in": 900}
```

Каждый обмен **ротирует** refresh-токен: старый инвалидируется в момент
использования, даже если что-то пойдёт не так дальше — повторное предъявление
уже потраченного токена (например, украденной копии) не даёт второй попытки.
Полноценный детект кражи (отзыв всей цепочки при обнаружении повторного
использования) не реализован — для демо-уровня достаточно самой ротации.

### Мгновенный logout — только в auth-сервисе

Access-токен — самоподписанный JWT: `wallet-api`/`wallet-gateway` проверяют
его подпись и `exp` сами по JWKS, вообще не спрашивая ничего у `google-auth`
на каждый запрос (это и есть весь смысл схемы, см. «Проверка токенов другими
сервисами» выше) — поэтому естественным путём отозвать access-токен раньше
его `exp` там нельзя без похода в auth на каждый запрос, а это разрушило бы
саму идею.

`auth::authenticate()` внутри **этого** сервиса — другое дело: помимо
подписи/`exp` он ещё проверяет, что хэш токена присутствует в Redis
(`repo::is_access_token_active`). `POST /auth/logout` удаляет эту запись
(`repo::revoke_access_token`) — значит `GET /auth/me` и `/admin/*` перестают
принимать этот токен мгновенно, а не только по истечении `exp`. На
`wallet-api`/`wallet-gateway` это не действует: их access-токен продолжит
проходить проверку по JWKS до истечения `exp` (по умолчанию до 15 минут) —
если нужен мгновенный отзыв и там, придётся либо научить их спрашивать тот же
Redis (и тогда пропадает смысл держать их stateless), либо смотреть в сторону
короче TTL/более частого refresh.

### Удаление аккаунта (`DELETE /auth/me`)

Самообслуживание — "Удалить аккаунт" в настройках wallet-web (по прямому
запросу, 2026-09-14). Аутентификация — тот же `authenticate()`, что и
`GET /auth/me`/`/admin/*`; действие — `repo::revoke_all_user_tokens` (тот же
примитив, что и принудительный logout из `/admin/users`, см. выше) ПОТОМ
жёсткий `DELETE FROM users WHERE id = $1` (`repo::delete_user`), потом
обнуляющие cookie — тот же порядок и тот же набор cookie, что у обычного
`POST /auth/logout`.

Порядок "сначала токены, потом строка `users`" принципиален: наоборот
оставалось бы окно, где ещё не истёкший access-токен продолжает проходить
`authenticate()` для уже не существующего пользователя. Без каскадов в этой
базе — единственный внешний ключ, ссылающийся на `users`, это её же
`role_id` НА `roles` (не наоборот), так что удаление строки `users` не
затрагивает ничего больше здесь. Идемпотентно — повторный вызов на уже
удалённом/незнакомом `id` просто не находит строк, не ошибка.

**Не удаляет данные пользователя в wallet-api** (леджер, счета, операции) —
это отдельный, независимый вызов `DELETE /api/account` там же (своя база,
своя схема, см. её README, "Удаление аккаунта"). Два разных сервиса, общей
транзакции нет — wallet-web вызывает СНАЧАЛА `wallet-api`, ПОТОМ этот
эндпоинт: обрыв между ними оставляет пользователя без данных, но ещё
способным войти и повторить весь сценарий (оба удаления идемпотентны), а не
идентичность, которая переживает данные, которым принадлежала.

### Роли: user / support / admin

`UserRecord::role` (enum, `types.hpp`) — три значения, кладутся в собственный
JWT как строковый claim `"role"` (`auth::issue_tokens`). Вычисляется по
`ADMIN_EMAILS`/`SUPPORT_EMAILS` (через запятую, см. `.env.example`; требуется
`email_verified` от Google — непроверенный email не может назначить себе
роль; если email есть в обоих списках — побеждает `admin`) — но **только
один раз, при первом логине** этого пользователя (см. `repo::upsert_user`):
дальше это не профильные данные из Google, а авторизационное состояние, и
повторные логины его не трогают.

Практическое следствие: добавление email в `ADMIN_EMAILS`/`SUPPORT_EMAILS`
подействует только на пользователей, которых ещё нет в `users` — уже
существующих придётся повышать/понижать явной правкой `users.role_id` в БД
(см. ниже). Симметрично: удаление email из списков **не** отзывает роль у
уже заведённого пользователя автоматически — тоже нужна ручная правка
`role_id`.

В БД роль хранится не текстом, а `users.role_id` — FK на справочник `roles`
(id/code/description, см. `google-auth/migrations/000001_init.up.sql` в корне
репозитория — схему накатывает `infra/db/migrate.sh`, не этот сервис, см.
«Персистентность» ниже); id
зафиксированы (1 `user`, 2 `support`, 3 `admin`) и совпадают с
`types.hpp::to_role_id()`/`role_from_id()`. Чтобы поменять роль уже
существующему пользователю:
```sql
UPDATE users SET role_id = 3 WHERE email = 'someone@example.com'; -- 3 = admin
```
Такая правка переживёт сколько угодно последующих логинов — `role_id`
существующего пользователя `upsert_user` не трогает вообще (см. выше), даже
если `ADMIN_EMAILS`/`SUPPORT_EMAILS` говорят другое.

В самом этом сервисе роль сейчас проверяется в двух местах —
`admin.cpp` (доступ к `/admin/users`, и к принудительному logout других
пользователей там же, только `Role::Admin`). Раньше здесь же жила вторая
проверка — доступ `support`/`admin` к чужим кошелькам (`wallet.cpp
::can_read/can_write`) — она уехала вместе с кошельками в
[wallet-api](https://github.com/WalletTransactions/wallet-api); тот сервис её сознательно не переносил (владелец,
без исключений, см. его README, "Что реализовано, а что нет"), но claim
`role` в токене всё ещё доступен, если это понадобится там в будущем.

### Аватарка (`picture`)

`UserRecord::picture` — URL Google-аватарки пользователя, приходит в
`GoogleClaims.picture` из тела `id_token` при логине (`google.cpp`) и
сохраняется в `users.picture` (`repo::upsert_user`, `ON CONFLICT DO UPDATE
SET ... picture = EXCLUDED.picture` — обновляется при КАЖДОМ логине, в
отличие от `role_id`, см. выше). До 2026-09-06 сохранялось в БД, но наружу
нигде не отдавалось (кроме мимолётной страницы подтверждения регистрации,
`pages.cpp::confirm_signup`, — она берёт `PendingSignup.picture`, отдельный,
недолговечный путь через `AppState::pending_signups`, не связанный с этой
колонкой).

По прямому запросу ("добавь в угол аватарку пользователя и имя" — для
сайдбара `wallet-web`) сначала был добавлен как claim `"picture"` в сам
access-JWT — и тут же справедливо отвергнут пользователем: presentational-
поле не имеет дела в токене, который летает с КАЖДЫМ запросом ко всему
`/api/*`/`/admin/*`, только ради одного экрана, читающего его один раз.
Токен — про идентичность и авторизацию (`sub`/`email`/`name`/`role`, и даже
`name`/`email` в нём уже давно, не только `role`), не про профильные поля
для отрисовки.

Вместо этого — отдельный, штучный поход в Postgres РОВНО там, где он нужен:
обработчик `GET /auth/me` (единственное место, которое SPA дёргает один раз
при загрузке страницы, см. README wallet-web) вызывает уже существующий
`repo::find_user_by_id()` и кладёт `record->picture` в JSON-ответ отдельным
полем (пустая строка, если аватарки нет — не `null`; `nullopt` от
`find_user_by_id` — только если пользователя успели удалить между выдачей
ещё живого токена и этим запросом, тогда тоже пустая строка, не 401: сама
аутентификация уже прошла). `AuthUser`/JWT `picture` не касаются вообще —
`authenticate()`, вызываемый на КАЖДОМ защищённом эндпоинте этого сервиса,
как был без обращения к БД (см. "Мгновенный logout" ниже про его вообще-то
единственный Redis-поход), так и остался.

### Список пользователей — агрегаты (`created_at`/`last_login_at`/`active_sessions`)

По прямому запросу — админ-таблица должна показывать не только email/роль,
но и когда пользователь зарегистрировался, когда заходил последний раз и
сколько у него сейчас живых сессий. Все три поля — в `users`/Redis этого же
сервиса, добавлять здесь было практически бесплатно:

- **`created_at`** — уже была в схеме (`000001_init.up.sql`), просто не
  попадала в ответ `GET /admin/users` (см. `admin.cpp::user_to_json`).
- **`last_login_at`** — новая колонка (`google-auth/migrations/
  000003_last_login.up.sql`). В отличие от `role_id` (авторизационное
  состояние, меняется только явной правкой в БД, см. «Роли» выше),
  `last_login_at` — обычные профильные данные и обновляется на **каждый**
  логин, и на `INSERT`, и на `ON CONFLICT` (`repo::upsert_user`). Пустая
  строка — пользователь заведён до этой миграции и ни разу не логинился
  после (не выдумываем дату, которой не знаем).
- **`active_sessions`** — не отдельное хранилище, а `repo::list_user_sessions`
  (тот же список, что строит `GET /auth/devices` самому пользователю про
  себя), просто длина списка. N пользователей — N обращений в Redis;
  для staff-таблицы, открываемой вручную и нечасто, это приемлемо — см.
  комментарий в `admin.cpp`, когда стоит переделать под batch.

Кошельки/операции/леджеры сюда сознательно не входят — они живут в другой
базе, у другого сервиса; тот же экран `/admin/users` дозапрашивает их
отдельно с `POST /api/reports/admin/users/stats` на `wallet-report` (по id из этого списка) и сшивает по
`user_id` на клиенте (см. README wallet-report, "Админ: агрегаты по
пользователям и «Посмотреть как клиент»", и `../wallet-web/site/app.js::
renderAdmin()`) — этот сервис намеренно не ходит в чужую БД сам.

### Принудительный logout (кнопка «Разлогинить» на `/admin/users`)

`POST /admin/users/:id/logout` — только `Role::Admin`. Отзывает **все**
активные access- и refresh-токены указанного `user_id` разом
(`repo::revoke_all_user_tokens`), а не один конкретный токен, как обычный
`/auth/logout`: пользователь мог залогиниться с нескольких устройств/
браузеров, каждый со своей парой токенов, обычный `/auth/logout` знает
только про токен из cookie текущего запроса.

Технически это обратный индекс в Redis: `store_access_token`/
`store_refresh_token` (см. `repo.hpp`) при каждой выдаче дополнительно
кладут хэш токена в множество `user_access_tokens:<id>` /
`user_refresh_tokens:<id>` (TTL = тот же, что у самого токена) — иначе по
`user_id` невозможно найти "все его токены", Redis не умеет "искать ключи по
значению". Принудительный logout читает оба множества, удаляет все токены
по найденным хэшам и сами множества. Тем же проходом удаляются MCP-токены
пользователя (`user_mcp_tokens:<id>`, см. «MCP-токены» ниже).

Действует та же оговорка, что и у обычного отзыва access-токена — см.
«Мгновенный logout — только в auth-сервисе» выше: `wallet-api`/
`wallet-gateway` проверяют токен по JWKS локально и про отзыв не узнают,
их access-токен "работает" до истечения `exp` (обычно 15 минут), даже если
пользователя только что принудительно разлогинили здесь.

### Устройства (self-service, `GET/POST /auth/devices*`)

В отличие от принудительного logout выше (только `Role::Admin`, управляет
чужими сессиями) — это то же самое для СЕБЯ: пользователь видит список своих
активных сессий и отзывает одну или все, кроме той, из которой пришёл сам
запрос. Реализовано в `devices.cpp`, экран — `wallet-web`
(`site/app.js::renderDevices()`).

- `GET /auth/devices` — активные (непросроченные) сессии текущего
  пользователя (`repo::list_user_sessions` — `GET`, не `GETDEL`: список не
  должен тратить refresh-токен самим фактом показа), с флагом `is_current` у
  той самой, из которой пришёл запрос. В список входят и персональные
  MCP-токены (`platform: "mcp"`, `device_name` — имя токена, `is_current`
  всегда `false`, см. «MCP-токены» ниже). У каждой сессии есть
  `last_used_at` и `expires_at` (ISO 8601 UTC или `null`):
  - refresh-сессия: `last_used_at` — момент выпуска текущего refresh-токена
    (вход или последний `/auth/refresh`; поле `issued_at` записи в Redis, у
    сессий старше этого поля — `null`), `expires_at` — срок refresh-токена;
  - MCP-сессия: `last_used_at` — последний успешный обмен (`null` до
    первого), `expires_at` — текущий скользящий срок.

  `expires_at` берётся из срока ключа в Redis (`EXPIRETIME`, Redis ≥ 7.0) —
  единственного источника правды, который есть и у старых записей. Просмотр
  ничего не продлевает.
- `POST /auth/devices/revoke {"token_hash", "refresh_token"?}` — отзывает
  одну конкретную, кроме текущей (для неё явная ошибка — используйте
  `/auth/logout`). `token_hash` — тот же непрозрачный id, что в списке;
  проверяется, что он принадлежит СВОЕМУ списку сессий, не любому в Redis.
- `POST /auth/devices/revoke-others {"refresh_token"?}` — отзывает все,
  кроме текущей, включая все MCP-токены (они входят в `revoked`).

Отзыв MCP-сессии удаляет MCP-токен: следующий обмен получает `401`, уже
выданный JWT обмена живёт до своего `exp` (не дольше 300 с).

Как определяется "текущая" (`GET /auth/devices`, флаг `is_current`, и
проверка "это не она" у обоих `POST` выше) — по приоритету:

1. **Точно**, если в запросе передан РЕАЛЬНЫЙ refresh-токен этой сессии —
   браузер присылает его в cookie (`refresh_token`, `Path=/auth`)
   автоматически, а клиенту без cookie jar (мобильный) достаточно передать
   то же поле `refresh_token` в теле — то же самое, что уже принимает
   `POST /auth/refresh` для таких клиентов. Хэш сверяется с
   `SessionSummary.token_hash`.
2. **Эвристикой**, если явного токена в запросе нет — по `device_id` из
   проверенного access-JWT запроса (см. `auth::AuthUser::device_id`): любая
   сессия с тем же `device_id` считается текущей. Корректно только потому,
   что схема гарантирует не больше одной активной сессии на устройство (см.
   "Схлопывание по `device_id`" ниже) — при явном токене эта эвристика не
   нужна вовсе, поэтому первый способ приоритетнее. Браузеру он почти не
   нужен — его refresh-cookie и так приходит с каждым запросом к `/auth/*`.
3. Ни то ни другое — "текущую" определить нечем: `/auth/devices/revoke-others`
   отвечает `400`, а не гадает, кого не трогать (слепое "отозвать всё" в
   этом случае опаснее ошибочного отказа).

**Мобильному клиенту стоит передавать `refresh_token` явно** в обоих `POST`
выше — точнее эвристики по `device_id` и не зависит от того, держится ли
инвариант "одна сессия на устройство" (например, если он на минуту нарушен
гонкой двух параллельных входов одного устройства).

**Схлопывание по `device_id` — на выпуске токенов, не на показе списка.**
Мобильный вход может пройти повторно для уже известного `device_id` без
выхода из старой сессии того же устройства (переустановка приложения,
повторный вход) — раньше это тихо копило несколько параллельных активных
refresh-сессий одного физического устройства, каждую до её собственного
TTL. Решение — держать инвариант "не больше одной активной сессии на
`(user, device_id)`" в единственной точке выпуска токенов
(`auth::issue_tokens`): непустой `device_id` перед записью новой сессии
отзывает все существующие сессии ТОГО ЖЕ `device_id`. Экран "Устройства"
поэтому просто ничего не группирует — дублей одного устройства там в
принципе не бывает. Браузер схлопыванием фактически не задет: его
`device_id` — новый UUID на каждый вход (см. ниже), совпасть ему не с чем,
и разные вкладки/браузеры одного человека остаются разными сессиями.

**`device_id` у браузера.** Браузер не даёт стабильного id устройства,
поэтому сервис выдаёт его сам: `google.cpp::browser_device` кладёт новый
UUID v4 в каждую браузерную сессию (`platform=web`), а
`auth::rotate_refresh_token` выдаёт его лениво сессиям, выпущенным раньше, —
на первом же `/auth/refresh` (`auth::ensure_browser_device_id`). Он попадает
в access-JWT, как у мобильного, — без него wallet-api отвечает на `/sync/*`
`403`, а веб пишет операции через `POST /sync/push`. Следствие: в wallet-api
на каждый вход в браузере заводится своё устройство `platform=web`.

**Отзыв сессии гасит и её парный access-токен, не только refresh.**
`store_refresh_token` кладёт в Redis рядом с устройством ещё и хэш
access-токена, выпущенного в той же паре (`access_token_hash`) — именно эта
связка, а не совпадение `device_id` (у браузерных сессий, выпущенных до
выдачи им `device_id`, он пуст до первого рефреша), позволяет `repo::revoke_user_sessions_if` погасить
ровно ОДИН access-токен нужной сессии, а не все токены пользователя разом
(как это делает `revoke_all_user_tokens` у admin force-logout). Это
касается и авто-схлопывания по `device_id` выше — старая сессия того же
устройства теряет доступ сразу, а не донашивает свой TTL.

Действует та же оговорка, что и у «Мгновенный logout — только в
auth-сервисе» выше: мгновенно, но ТОЛЬКО для проверок, которые делает сам
этот сервис (`auth::authenticate()` смотрит в Redis) — `wallet-api`/
`wallet-gateway` проверяют access-токен по JWKS локально, в Redis вообще не
заглядывают и про этот отзыв никогда не узнают: тот же самый access-токен у
них продолжит "работать" до истечения `exp` (обычно 15 минут), сколько бы
записей о нём ни удалили здесь. Закрыть и этот путь можно только ценой
другого компромисса — либо укоротить `ACCESS_TOKEN_TTL_SECS`, либо заставить
`wallet-api`/`wallet-gateway` тоже спрашивать Redis на каждый запрос (это и
есть тот сетевой поход в auth на каждый запрос, ради ухода от которого и
выбран JWKS, см. `server-sync-design-decisions`) — на этом этапе принят как
известное ограничение, не как недосмотр.

### MCP-токены (`POST /auth/mcp-tokens`, `/internal/mcp/token`)

Персональный токен для MCP-клиента (LM Studio, позже Claude Code и др.),
через который `wallet-mcp` читает кошелёк пользователя. MCP-клиент держит в
`mcp.json` статичный заголовок `Authorization` и не умеет ни входить через
Google, ни ротировать refresh, а 15-минутный access-JWT в конфиг не положить.
Реализовано в `mcp_tokens.cpp`, хранилище — в `repo.cpp` рядом с refresh
(change `add-mcp-personal-tokens`).

**Выпуск.** Вошедший пользователь (веб, «Мои устройства») вызывает
`POST /auth/mcp-tokens {"name": "LM Studio дома"}` и получает `201
{"token", "device_id", "name", "expires_at"}`. Токен —
`wmcp_<base64url от 32 случайных байт>` (48 символов), показывается ОДИН
раз: в Redis лежит только `mcp_token:<base64url(sha256)>` →
`{user_id, device_id, name, created_at, cap_at, last_used_at}` и индекс
`user_mcp_tokens:<user_id>`. Имя обрезается по краям, 1..64 символа (иначе
`400`). Не больше **10** активных MCP-токенов на пользователя — сверх лимита
`409`; отозванные и истёкшие не считаются. Аутентификация — как у всех ручек
аккаунта (`aud` `google-auth`, scope `account`): токен бота и JWT обмена
получают `401`. Тело ответа не пишется в debug-журнал (`secret_body` в
`main.cpp`).

**Срок: 30 дней скольжения, 90 дней потолок.** Токен умирает через 30 дней
без успешного обмена; каждый обмен переносит срок на
`min(обмен + 30 дней, выпуск + 90 дней)`. За 90 дней от выпуска не
продлить — только выпустить новый. Оба срока выражены сроком ключа Redis
(`SET … EXAT`, на обмене `SET … XX EXAT`, чтобы не воскресить ключ,
отозванный между чтением и записью), фоновой чистки нет. Потолок
дублируется проверкой в коде на случай сдвига часов. Наружу отдаётся только
текущий срок (`expires_at`), сам потолок — нет.

**Обмен.** `wallet-mcp` из сети контура вызывает
`POST /internal/mcp/token {"token": "wmcp_…"}` и получает `200
{"access_token", "expires_in": 300, "user_id", "device_id"}`. Общего
секрета нет: доказательство — сам токен (256 бит). JWT RS256:

| claim | значение |
| --- | --- |
| `sub` | id пользователя |
| `iss` | `google-auth` |
| `aud` | `["wallet-report"]` |
| `scope` | `reports:read` |
| `device_id` | `device_id` MCP-токена |
| `platform` | `mcp` |
| `iat`, `exp` | `exp` = `iat` + 300 |

**Без `role`, `email`, `name`** (`token_claims::add_mcp_claims`, тест в
`tests/test_token_claims.cpp`): wallet-report видит обычного пользователя,
админский `as_user_id` через MCP недоступен даже администратору. JWT в Redis
не регистрируется — google-auth его не принимает (нет `aud` `google-auth`),
ни записать в wallet-api, ни вызвать wallet-ai им нельзя. Обмен проверяет,
что пользователь ещё существует (иначе ключ удаляется). Любой отказ —
`401 {"error":"invalid_token"}`, причины наружу не различаются (только в
журнале, событие `mcp_token_rejected` с `reason`, без токена и хэша).
Потребители: wallet-report (проверяет подпись, `exp`, `iss`, `aud`, scope —
правок не требует) и wallet-mcp (клиент обмена, кеширует JWT до `exp`).

**Отзыв.** MCP-токен — сессия устройства: `POST /auth/devices/revoke`,
`revoke-others`, `DELETE /auth/me` и `POST /admin/users/{id}/logout` гасят
его. Уже выданный JWT обмена живёт до `exp` (до 300 с) — как токен бота.
`POST /auth/refresh` MCP-токен не принимает: другой префикс ключа, обычный
`401` про refresh, MCP-токен при этом цел. И наоборот: refresh-токен на
обмене — `401`, и он не тратится.

`/internal/mcp/token` гейтвеем не проксируется (`/internal/*`), но прямой
порт google-auth его открывает — как и `/internal/telegram/*`. Перебор
бессмыслен (256 бит), ограничения частоты нет; сетевые политики —
`org/docs/TODO_service_auth_tls.md`.

Метрики: `mcp_tokens_issued_total{result="ok"}`,
`mcp_token_exchanges_total{result="ok|invalid"}`. Журнал:
`mcp_token_issued`, `mcp_token_exchanged` (`user_id`, `device_id`),
`mcp_token_rejected`.

### Telegram-бот (`POST /auth/telegram/link-code`, `/internal/telegram/exchange`)

Сторона google-auth для бота `wallet-telegram` (план —
`org/docs/TODO_telegram_bot.md`, §1.2), реализовано в `telegram.cpp`. Бот —
обычное устройство пользователя с `platform=telegram`: отдельной модели
доступа для него нет.

1. Залогиненный пользователь (веб) вызывает `POST /auth/telegram/link-code`
   и получает одноразовый код (24 случайных байта в base64url, TTL
   `TELEGRAM_LINK_CODE_TTL_SECS`, по умолчанию 10 мин) плюс
   `deep_link = https://t.me/<TELEGRAM_BOT_USERNAME>?start=<code>`. В Redis
   лежит `tg_link_code:<sha256(code)>` → `user_id`, без самого кода.
2. Пользователь открывает ссылку и жмёт Start. Бот получает
   `/start <code>` и вызывает `POST /internal/telegram/exchange` с
   заголовком `X-Service-Secret`. Код забирается `GETDEL` — второй обмен
   того же кода даёт 410.
3. В ответ бот получает обычную пару токенов устройства. `device_id`
   детерминирован от `(user_id, tg_user_id)`, поэтому повторное связывание
   того же чата заменяет прежнюю сессию (см. схлопывание в
   `auth::issue_tokens`). Сессия видна в `GET /auth/devices` как
   «Telegram @username» и отзывается там же — после этого первый же
   `/auth/refresh` бота даёт 401.

`/internal/*` wallet-gateway не маршрутизирует: неизвестный префикс уходит в
статику SPA. Прямой порт google-auth (`8080:8080` в `compose.yaml`) этот
путь открывает, поэтому единственная защита на нём — секрет. Без
`TELEGRAM_SERVICE_SECRET` эндпоинт выключен (503), а не открыт.

`platform` в `POST /auth/google/mobile` проверяется белым списком
(`android/ios/web/other`, `types.hpp::is_mobile_login_platform`), так же как
CHECK `device.platform` в wallet-api. Иначе неизвестное значение давало бы
валидный токен и 500 на первом `/sync/*`. `telegram` в этот список не
входит: такую сессию выдаёт только обмен кода.

### Кнопки-самотесты на странице успеха

После входа страница показывает три кнопки — «Проверить вставку», «Проверить
удаление», «Выйти» — которые прямо из браузера дёргают `POST`/`DELETE
/api/wallets` (на wallet-api) и `POST /auth/logout` (на этом сервисе) через
`fetch()`, авторизация — той же cookie `session`, без ручного ввода токена.
Работает без CORS-проблем ровно потому, что страница открыта через
[wallet-gateway](https://github.com/WalletTransactions/wallet-gateway) — см. "Через гейтвей, не напрямую" выше:
её origin `:8090`, туда же уходит relative `fetch('/api/wallets')`, а гейтвей
проксирует на wallet-api. Если же открыть success-страницу напрямую на
`:8080` (в обход гейтвея) — кнопки получат `404`, wallet-api там не слушает;
страница показывает под кнопками и `curl`-пример на случай такой проверки
без браузера/гейтвея.

Обёртка `apiFetch()` в JS страницы сама ловит `401` от истёкшего access-токена,
один раз дёргает `POST /auth/refresh` (по cookie `refresh_token`) и повторяет
исходный запрос — если постоять на странице дольше 15 минут и потом нажать
кнопку, она не должна упасть с 401, а прозрачно обновит сессию.

## Мобильный вход (Android Credential Manager)

Второй способ получить ту же пару токенов, что и браузерный флоу
(`/auth/google` → `/auth/google/callback`) — но без редиректа и обмена
`code`: Android получает `id_token` от Google напрямую через Credential
Manager (Play Services), минуя браузер целиком. Сервер видит уже готовый,
подписанный Google `id_token` и верифицирует его тем же кодом
(`verify_id_token`), что и браузерный колбэк — audience всё та же **Web**
client ID (см. "1. Получить Client ID" выше); *в коде* отдельный Android
OAuth client не нужен нигде.

**Но завести его в Google Cloud Console всё равно придётся** (найдено
2026-09-04 на реальном устройстве) — это не то же самое, что "не нужен
вообще". Play Services на устройстве, прежде чем выдать `id_token` через
`GetGoogleIdOption`, сам проверяет, зарегистрирован ли вызывающий пакет
(package name + SHA-1 сертификата подписи APK) как Android-клиент в том же
проекте — независимо от того, что сервер потом верифицирует токен по Web
client ID, а не по этому Android-клиенту. Без такой записи Play Services
не идёт даже до выбора аккаунта — отдаёт `NoCredentialException: No
credentials available`, что выглядит как "на телефоне нет Google-аккаунта"
(да ещё и на пункт неверный, диагностировать не с первого взгляда).

Завести: **Google Cloud Console → APIs & Services → Credentials → Create
Credentials → OAuth client ID → Android**, package name
`com.example.wallettransactions`, SHA-1 сертификата подписи APK (для
debug-сборки — `keytool -list -v -keystore ~/.android/debug.keystore
-alias androiddebugkey -storepass android -keypass android`, каждый
подписывающий сертификат — debug и, отдельно, будущий release — своей
записью). В коде этот client ID нигде не используется — только
факт его существования в проекте.

Раз тут нет ни `code`, ни PKCE, от повторного использования перехваченного
`id_token` защищает **nonce**:

```bash
curl -X POST http://localhost:8090/auth/nonce
# -> {"nonce": "..."}
```

Клиент передаёт этот `nonce` в `GetGoogleIdOption.setNonce(...)` **до**
вызова Credential Manager — Google подписывает его прямо внутрь `id_token`
(claim `nonce`), и сервер потом сверяет его со своим выданным набором,
атомарно удаляя найденный (`AppState::issued_nonces`, в памяти — тот же
уровень строгости, что у `pending`/`pending_signups`, см. комментарий в
`app_state.hpp`: рестарт сервиса просто заставит начать вход заново, ничего
не теряя, потому что аккаунт до успешного входа не создаётся).

```bash
curl -X POST http://localhost:8090/auth/google/mobile \
  -H "Content-Type: application/json" \
  -d '{"id_token": "...", "device_id": "...", "device_name": "Pixel 7", "platform": "android"}'
# -> {"access_token": "...", "refresh_token": "...", "expires_in": 900}
```

Отличия от браузерного флоу:

- **Нет cookie.** Мобильный клиент не имеет cookie jar — токены только в
  теле JSON-ответа, клиент хранит их сам (Android — в
  `EncryptedSharedPreferences`, см. `org/docs/TODO_mobile_sync.md`, Фаза 3).
- **Нет страницы подтверждения регистрации.** У браузерного флоу для нового
  `google_sub` есть промежуточный шаг — HTML-страница «Создать аккаунт?»
  (см. «Регистрация» выше). Для мобильного этот шаг избыточен: сам тап
  «Войти через Google» в приложении уже и есть явное действие пользователя,
  а рендерить HTML для этого шанса пришлось бы через WebView. Аккаунт
  создаётся сразу тем же `get_or_create_user`, что и подтверждённая
  регистрация в браузере.
- **`device_id` обязателен** (`device_name`/`platform` — нет, `platform`
  по умолчанию `"android"`). См. "Детали устройства" ниже.
- Дальше — `/auth/refresh`/`/auth/logout` те же самые, что и у браузерного
  флоу (см. «Обновление сессии» выше): формат токена не отличает, откуда
  пришёл логин.

### Детали устройства (`DeviceInfo`)

И браузерный, и мобильный вход сопровождают выпущенную пару токенов
данными об устройстве (`DeviceInfo`, `types.hpp`) — откуда взялся вход, а не
только кто вошёл:

| Поле | Браузер | Мобильный |
| --- | --- | --- |
| `device_id` | новый UUID на каждый вход, выдаёт сервис (у браузера нет стабильного id); у старых сессий — на первом `/auth/refresh` | обязателен — генерирует клиент один раз при установке и хранит локально (Android — `AppSettings.getOrCreateDeviceId`, обычный UUID, не android_id/IMEI) |
| `device_name` | сырой `User-Agent` запроса, как есть | из тела запроса, например `"Pixel 7"` — только для показа человеку |
| `platform` | `"web"` | из тела запроса, по умолчанию `"android"` |

Дальше это работает так:

- **Хранится вместе с refresh-токеном** (`repo::store_refresh_token` кладёт в
  Redis не голый `user_id`, а JSON с этими тремя полями) — и **переживает
  ротацию**: `POST /auth/refresh` переносит те же поля на новую пару
  (`auth::rotate_refresh_token` → `repo::take_refresh_token` возвращает
  устройство обратно), а не только на первый логин. Без этого "какое это
  устройство" терялось бы уже на первом рефреше.
- **Непустой `device_id` дополнительно попадает в сам access-JWT** (claim
  `device_id`, и `platform` рядом с ним) — так `wallet-api` получает id
  устройства уже **проверенным подписью**, а не из непроверяемого
  клиентского заголовка. Это сознательное отличие от более ранней
  формулировки плана (`org/docs/TODO_mobile_sync.md`, п. 1.2): изначально
  предполагался отдельный заголовок `X-Device-Id`, но раз устройство и так
  устанавливается один раз при входе и живёт вместе с сессией — надёжнее
  положить его в то же самое место, что уже доверено (подписанный токен),
  чем заново придумывать доверие к отдельному значению на каждый запрос.
- **`iss`, `aud`, `scope`** (2026-09-29, `org/docs/TODO_telegram_tokens.md`,
  шаг 1) — в каждом access-токене: `iss: "google-auth"`,
  `aud: ["wallet-api", "wallet-report", "google-auth"]` — сервисы, которые
  сами проверяют токен, `scope: "wallet:read wallet:write account"` — полный
  набор пользователя. Значения — `src/token_claims.hpp`, их же берёт
  `tools/mint_loadtest_token`. Проверяют все сервисы и гейтвей (шаг 2);
  токен без `aud` с 2026-10-22 отклоняется везде — 401 (шаг 3). Урезанный токен
  Telegram-бота (без `google-auth` в `aud`, `scope: "reports:read
  expense:write"`) — шаг 4; до него сессия бота получает тот же полный набор.
  С 2026-10-11 (`org/docs/TODO_wallet_ai.md`, §2) у обоих токенов в `aud`
  есть `wallet-ai`, в `scope` — `ai:use` (доступ к LLM-функциям).
- Старый формат значения в Redis (просто `user_id` строкой, до этого поля)
  `take_refresh_token` по-прежнему понимает — падать на нём не должен,
  просто вернёт устройство пустым.

Что дальше, но не сделано сейчас: показать пользователю (или админу) список
активных устройств и отозвать одно конкретное — сейчас `POST
/admin/users/:id/logout` отзывает все сессии сразу
(`repo::revoke_all_user_tokens`), поштучно пока нельзя, хотя данные для
этого (`user_refresh_tokens:<id>` → JSON с `device_name`/`platform` для
каждого) уже лежат в Redis.

## Кроссплатформенность (Windows / Linux)

Один и тот же `CMakeLists.txt` и исходники собираются на обеих ОС без правок.
TLS-клиент к Google (cpp-httplib + OpenSSL) по умолчанию использует
**системное хранилище сертификатов** (Windows Certificate Store через
`crypt32`/Schannel, доверенный root store на Linux) — отдельный CA-бандл не
нужен. Если на машине (например, в минимальном Docker-контейнере без пакета
`ca-certificates`) системного хранилища нет, укажите в `.env`:

```
CA_BUNDLE_PATH=third_party/cacert.pem
```

(бандл Mozilla уже лежит в репозитории, актуализировать — с https://curl.se/ca/cacert.pem).

На Linux-сервере, слушающем внешние подключения, поставьте `HOST=0.0.0.0` и
поместите сервис за reverse-proxy (nginx/caddy) с HTTPS — Google требует
HTTPS для `redirect_uri`, кроме `localhost`.

## Установка и запуск как служба

`cmake --build` сам кладёт нужные скрипты рядом с готовым бинарником (см.
`scripts/windows/` и `scripts/linux/` в репозитории — источники этих же
файлов, на случай ручного развёртывания на другой машине без пересборки).

### Windows (`build/Release/`)

Служба ставится через [NSSM](https://nssm.cc/) — `google_auth.exe` сам по
себе обычная консольная программа, а не служба Windows (не делает SCM-хендшейк),
поэтому нужен обёртчик; `install-service.bat` это делает автоматически.

1. Положите готовый `.env` в `build/Release/` (рядом с `google_auth.exe`) — см. `.env.example`.
2. Если `nssm` не установлен: `winget install -e --id NSSM.NSSM`, затем откройте новое окно консоли.
3. Запустите `install-service.bat` (двойным щелчком или из консоли) — сам запросит права администратора, установит и сразу запустит службу `google-auth`. Логи — `service-stdout.log` / `service-stderr.log` там же.

Дальше: `start-service.bat`, `stop-service.bat`, `uninstall-service.bat` — управление службой.
Есть также `run-console.bat` — запустить `google_auth.exe` напрямую в консоли без установки службы, для быстрой проверки.

### Linux (`build/`)

```bash
sudo ./install-service.sh          # ставит /opt/google-auth, юнит systemd, enable --now
sudo systemctl status google-auth
journalctl -u google-auth -f
sudo ./uninstall-service.sh        # останавливает и убирает юнит (файлы в /opt/google-auth не трогает)
```

Скрипт ищет `google_auth` рядом с собой (или путь первым аргументом:
`sudo ./install-service.sh /путь/к/бинарнику`) и копирует также лежащий
рядом `.env`, если он там есть — иначе перед первым запуском создайте
`/opt/google-auth/.env` вручную (см. `.env.example`).

На Linux-сервере, слушающем внешние подключения, поставьте `HOST=0.0.0.0` в
`.env` и поместите сервис за reverse-proxy (nginx/caddy) с HTTPS — Google
требует HTTPS для `redirect_uri`, кроме `localhost`.

## Логирование

Формат — одна JSON-строка на запись: `{"ts","level","service","trace_id"?,
"msg"}`, плюс для db-запросов (см. ниже) — `"sql"/"duration_ms"/"rows"`.
`level` — ровно одно из четырёх значений (`applog::error/warn/info/debug`,
см. `util/log.hpp`): `error` — реально мешает ответить клиенту осмысленно,
`warn` — заметили странность, но обработали и продолжили, `info` — обычный
ход событий (запрос обработан, сервис стартовал), `debug` — подробности
не для постоянного мониторинга. Само сообщение — всегда в `msg`, не
размазано по другим полям. Структурированный формат — чтобы логи парсились/фильтровались по полю
(jq/Loki/ELK), а не грепались как текст; `ts` — всегда UTC независимо от
таймзоны хоста. `trace_id` — сквозной id одного запроса браузера через все
сервисы (gateway → auth/wallet-api): его порождает только wallet-gateway
(единственная точка входа), остальные сервисы читают его из заголовка
`X-Trace-Id` — так по логам разных сервисов можно склеить путь одного
запроса (`grep trace_id` / `jq 'select(.trace_id=="...")'`).

*Куда* пишется — настраивается через `LOG_DIR` (`.env`), это отдельная ось от
формата строки. **Общая схема для всех сервисов проекта** (wallet-gateway,
wallet-api — см. их README) — папка с файлом на каждый календарный день:

- **По умолчанию на Windows** — папка `logs/` в рабочей директории, внутри
  файлы вида `2026-08-24-google-auth.log` (имя сервиса в имени файла — чтобы
  не путать с логами других сервисов проекта, если логи разных сервисов
  вдруг окажутся в одной папке) (у службы, поставленной через
  `install-service.bat`, нет консоли — смотреть вывод можно только в файле).
  Ротация — по смене даты: как только наступают новые сутки, следующая
  запись уходит уже в новый файл; старые файлы не трогаются и не
  удаляются — если нужно их подчищать/архивировать, это забота внешней
  системы (logrotate, задача в планировщике и т.п.), не самого сервиса.
- **По умолчанию на Linux/в Docker** — stdout/stderr, как и положено для
  контейнеров: раннтайм (Docker, systemd/journald) сам собирает логи с
  потоков вывода процесса; писать в файл внутри контейнера — антипаттерн,
  логи пропадут вместе с контейнером без отдельного volume.
- **Переопределить** можно в любую сторону: `LOG_DIR=var/log/google-auth` —
  свой путь к папке (создастся сама), `LOG_DIR=stdout` — принудительно
  консоль даже на Windows (например, для `run-console.bat`, если хочется
  смотреть вживую).

При запуске через `install-service.bat` (NSSM) получится два независимых лога
одновременно: свой `logs/<дата>-google-auth.log` (см. выше) и `service-stdout.log`/
`service-stderr.log` от самого NSSM — вторые обычно остаются пустыми (мы
больше не пишем в stdout по умолчанию на Windows) и служат просто
подстраховкой на случай падения до инициализации логгера.

**SQL-запросы** — каждый вызов `db::Database::exec()` (см. `db.cpp`) пишет
строку `"db query"` (или `"db query failed"` — с полем `"error"`) с
`sql` (сам текст запроса, с `$1/$2/...` — безопасно логировать всегда, это
не конкатенация строк), `duration_ms` (латенси именно самого запроса к
Postgres, без ожидания на мьютексе соединения) и `rows` (число вернувшихся
строк). Значения параметров ($1, $2, ...) в лог НЕ попадают по умолчанию —
это произвольные данные приложения (email и т.п.); включить можно
`LOG_SQL_PARAMS=true` в `.env`, только для локальной отладки.

Даже при включённом `LOG_SQL_PARAMS`, если вызывающий код указал параметру
имя через `param_names` (см. `exec()` в `db.hpp`) и это имя входит в список
маскируемых, значение в логе заменяется на `"***"` — независимо от флага.
Встроенный список (`password`, `client_secret`, `refresh_token`,
`access_token`, `id_token`, `token`, `secret` — см. `builtin_mask_param_names()`
в `db.cpp`) расширяется своими именами через `LOG_SQL_MASK_PARAMS` (CSV в
`.env`). Сейчас в Postgres этого сервиса секретов среди параметров запросов
нет (roles/users — google_sub/email/..., токены в Redis, см. ниже), механизм
— задел на будущее.

**`GET /healthz` не логируется вовсе** (ни `"request_finished"`, ни тело) —
это не запрос приложения, а probe `compose.yaml` (interval 10s), который по
логам не отличить от реального трафика, но который забивает их шумом
(~8640 строк/сутки) без всякой пользы: сама проверка ничего не открывает и
не пишет. Тот же приём — в `wallet-api`/`wallet-gateway`/`wallet-report`
(см. их `svr.set_logger` в `main.cpp`).

**Тело запроса/ответа** — на каждый обработанный запрос (кроме `/healthz`
выше), рядом со строкой `"request_finished"` (см. выше), пишется ещё одна,
уровня `debug`, с полями
`"event":"request_body"`, `"request_body"` и `"response_body"` — сырое тело
как оно есть (обрезается до 1024 байт с пометкой "...(обрезано, всего N
байт)", если больше — см. `truncate_body` в `main.cpp`). Лимит — в сырых
байтах тела, не в байтах итоговой строки лога: на бинарных телах (blob в
wallet-api) непечатные байты при JSON-экранировании раздуваются до 6
символов каждый, и на старом лимите 4096 байт строка лога иногда превышала
предел длины строки journald — тот резал её на куски
(`CONTAINER_PARTIAL_MESSAGE:true`), а fluent-bit (строгий JSON-парсер
app_json) не мог разобрать оборванный кусок и оставлял запись без
`level`/`service`/`trace_id`/`msg`, только сырой `message`. В отличие от
SQL-параметров, эта строка пишется ВСЕГДА, без отдельного флага —
единственная защита от постоянного мониторинга здесь — сам `level: "debug"`:
фильтруйте его прочь в jq/Loki, если не отлаживаете конкретный запрос. Тело
здесь может нести google id_token, refresh-токен, пароль и т.п. — тем более
не подключайте эти логи к системе, которую видит кто-то за пределами
разработки.

## Версия

Общая схема для всех C++-сервисов проекта (google-auth, wallet-api,
wallet-report, wallet-gateway, wallet-ai, wallet-telegram) — версия
проставляется на билде, не хардкодится в исходниках:

- **Источник** — файл `VERSION` рядом с `CMakeLists.txt` (semver, например
  `0.1.0`), правится руками при релизе. CMake читает его и генерирует
  `version.hpp` (`src/version.hpp.in` → `build/generated/version.hpp`, не
  коммитится, см. `CMakeLists.txt`, "Версия приложения").
- **Git-хэш** — ДОПОЛНИТЕЛЬНО к `VERSION`, отличает два билда с одним и тем
  же номером между релизами. При сборке образа (`Containerfile`) своего
  `.git` в контексте нет — хэш передаётся снаружи через `docker build
  --build-arg GIT_COMMIT=$(git rev-parse --short=8 HEAD)` (так делает CI,
  `.github/workflows/release.yml`). При
  нативной сборке на рабочей машине (`cmake -B build`) CMake сам спросит
  git. Не нашёл ни то, ни другое — `"unknown"`, сборка не падает.
- **Сборка (`build`)** — тег образа, `0.1.1-rc.2`. Release передаёт его через
  `--build-arg APP_BUILD` (Containerfile → `-DAPP_BUILD`), без него CMake
  ставит `<VERSION>-dev`. Это отдельное поле, а не замена `version`: по
  `version` smoke выката сверяет `X.Y.Z`. Финальный `X.Y.Z` — тот же образ,
  поэтому в prod `build` показывает, какой rc промоутнут.
- **Время запуска (`started_at`)** — момент вызова `metrics::set_build_info`
  в `main()` (wallet-common), ISO-8601 UTC.
- **Видно** так, везде одни и те же `service`/`version`/`build`/`git_commit`:
  - `GET /version` — JSON с ними и `started_at`, без авторизации (как
    `/healthz`, `/metrics`).
  - Строка лога при старте (`"... v<build> (hash) listening on ..."`).
  - `build_info{service,version,build,git_commit} 1` в `GET /metrics`, тот
    же приём, что у kube-state-metrics/большинства Prometheus-клиентов (не
    отдельная метрика на поле, один gauge с лейблами) — Grafana строит по
    нему таблицу "какой билд где крутится". Рядом —
    `process_start_time_seconds`.
  - Сводка всех сервисов контура — `GET /api/versions` гейтвея (только
    роль `admin`) и бейдж версии в углу веба.

### Релиз: git-тег → образ → контур

Общая для всех 7 сервисов (включая wallet-web). Стек работает в двух
контурах — test (`:8091`) и prod (`:8090`), см. `wallet-infra/infra/env/README.md`;
образы для них собирает только CI, на хосте ничего не собирается.

| Git-тег | Что делает CI (`.github/workflows/release.yml`) | Куда выкатывает Jenkins |
| --- | --- | --- |
| `vX.Y.Z-rc.N` | юнит-тесты, сборка, push `ghcr.io/wallettransactions/<сервис>:X.Y.Z-rc.N` | test, автоматически за ≤10 минут |
| `vX.Y.Z` | **без пересборки**: старший `vX.Y.Z-rc.*` на этом же коммите получает тег `X.Y.Z` (тот же digest) | prod — только если этот digest прошёл smoke в test |

Правила:

- `X.Y.Z` тега обязан совпадать с `VERSION` — иначе workflow падает. Порядок:
  поднять `VERSION` коммитом → `vX.Y.Z-rc.1` → проверить в test → при
  правках новый коммит и `vX.Y.Z-rc.2` → `vX.Y.Z` на коммит последнего rc.
- `vX.Y.Z` на коммит без rc — workflow падает, образ не публикуется: в prod
  попадает только то, что было в test.
- Миграции едут в образе (`/migrations`) и катятся до обновления сервиса;
  откат сервиса схему не откатывает — миграции пишутся по правилу
  expand/contract, см. `wallet-infra/infra/db/README.md`.
- Старые rc-версии в ghcr чистит `.github/workflows/packages-cleanup.yml`
  (оставляет 10 последних rc, финальные — все).

```bash
git tag v0.2.0-rc.1 && git push origin v0.2.0-rc.1   # → test
git tag v0.2.0      && git push origin v0.2.0        # → prod (тот же коммит)
```

## Персистентность (Postgres + Redis)

`users` живёт в Postgres (`DATABASE_URL`) — переживает рестарт сервиса
(`wallets` в этой БД больше нет — своя таблица в своей БД у wallet-api, см.
его README, "Своя БД"). Access- и refresh-токены — оба в Redis (см. ниже),
`refresh_tokens` в Postgres для этого сервиса больше не используется вообще.
`pending` (PKCE) и `pending_signups` (см. «Регистрация» выше) намеренно
остались в памяти процесса: обе структуры живут секунды-минуты в рамках
одного логина, терять их при рестарте не страшно — пользователь просто
начинает вход заново, ни разу не потеряв уже созданные данные.

**Схему этот сервис больше не создаёт сам.** Роль, которой он подключается
(`AUTH_POSTGRES_USER`/`.env` → `DATABASE_URL`), намеренно не имеет прав DDL
— ни `CREATE`/`ALTER`/`DROP`, ни `TRUNCATE` (см. `infra/db/README.md` в корне
репозитория, "Три роли" — три отдельных Postgres-роли: мигратор с правом
DDL на обе базы проекта, и по одной строго DML-роли на каждый сервис). Схему
(`roles`/`users`) накатывает `infra/db/migrate.sh auth up` (версионированные
миграции, [golang-migrate](https://github.com/golang-migrate/migrate) — см.
`google-auth/migrations/` и `infra/db/README.md`, "Миграции") — отдельным шагом ПОСЛЕ
старта `db`, но ДО старта самого `google-auth`. `init-db.sh` (тоже
мигратором, но автоматически при первом старте контейнера `db`) заводит
только роли/базы/права — саму схему больше не трогает.
`db::Database::verify_schema()` (вызывается при старте, см. `main.cpp`)
ничего не создаёт — только проверяет, что нужные таблицы уже есть, и падает
с понятной ошибкой, если нет (в т.ч. если миграции забыли накатить) —
вместо непонятного `permission denied` на первом же реальном запросе. На
инстансах, поднятых до переезда refresh-токенов в Redis, таблица
`refresh_tokens` могла физически остаться в базе — ничего её сейчас не
удаляет, сервис её просто больше не читает и не пишет.

Следствие: если менять существующие колонки/constraints (эволюция схемы) —
это новая пара `.up.sql`/`.down.sql` в `google-auth/migrations/`, накатывается
`infra/db/migrate.sh auth up` (см. `infra/db/README.md`), а не автоматически при старте
сервиса.

Одно соединение с БД на процесс, под мьютексом (см. комментарий в `db.hpp`) —
годится для масштаба демо-сервиса; под реальной нагрузкой нужен пул
соединений или PgBouncer перед сервисом.

**Access-токены — в Redis** (`REDIS_HOST`/`REDIS_PORT`/`REDIS_PASSWORD`, см.
`.env.example`): ключ `access_token:<base64url(sha256(токен))>` (тот же приём
хеширования, что и у refresh-токенов ниже — сам JWT в Redis не попадает),
значение — `user_id`, TTL = `ACCESS_TOKEN_TTL_SECS` (тот же срок, которым
подписан сам JWT). Redis `EXPIRE` сам удаляет запись по истечении — никакого
отдельного «сборщика мусора» не нужно. Смысл этого стора не в том, чтобы
знать, что токен валиден (это и так проверяет подпись/`exp` самого JWT), а в
том, чтобы `POST /auth/logout` мог удалить запись раньше срока — см.
«Мгновенный logout — только в auth-сервисе» выше про то, где именно это
работает, а где нет.

**Refresh-токены — тоже в Redis** (переехали из Postgres): ключ
`refresh_token:<base64url(sha256(токен))>`, значение — `user_id`, TTL =
`REFRESH_TOKEN_TTL_SECS` (30 дней по умолчанию). Ротация при каждом
`/auth/refresh` — атомарный `GETDEL` (Redis ≥ 6.2, читает и удаляет ключ
ОДНОЙ командой) вместо прежнего `DELETE ... RETURNING` в Postgres — тот же
принцип одноразовости, просто на новом бэкенде (см. `repo::take_refresh_token`).
Redis `EXPIRE` избавляет и здесь от накопления просроченного мусора, которым
раньше обрастала таблица `refresh_tokens` между использованиями токена (см.
`repo::store_refresh_token`).

**Redis-контейнер — с AOF-персистентностью и volume** (`--appendonly yes` +
volume `redis-data`, см. `compose.yaml`) — это ОБЯЗАТЕЛЬНО, в отличие от
чистого кэша: access-токены без персистентности пережили бы потерю данных
безболезненно (TTL короткий, 15 минут, `POST /auth/refresh` сам всё
исправит), но refresh-токены — единственное, что не даёт логиниться через
Google каждые 15 минут, и их TTL — 30 дней. Без персистентности любое
пересоздание контейнера (смена образа, `--build`, ручной `rm`) стёрло бы
разом refresh-токены ВСЕХ пользователей — принудительный релогин для всех, а
не тихое самоисправление. `appendfsync` не задан явно — берётся дефолт образа
(`everysec`), этого достаточно для объёма записи этого сервиса.

`users` (identity) остаётся в Postgres — ровно то, для чего он и нужен:
ACID, связи, долгая жизнь записи без TTL, куда Redis не годится в принципе.

## Продакшн-заметки

- JWKS Google запрашивается заново на каждый вход — в проде стоит кешировать по `Cache-Control` из ответа Google.
- `access_type=online` (без refresh_token у Google) — задача сервиса разовая верификация, а не долгоживущий доступ к Google API от имени пользователя (не путать с нашим собственным refresh-токеном — это другая, не Google-овская сущность).
- Ротация refresh-токена есть, полноценный детект кражи (отзыв всей цепочки при повторном использовании уже потраченного токена) — нет. Для прод-уровня безопасности стоит добавить: помечать скомпрометированной всю "семью" токенов, если бывший в употреблении токен предъявили повторно.
- `auth`/`wallet` уже разъехались в отдельные сервисы (см. [wallet-api](https://github.com/WalletTransactions/wallet-api)) — подпись асимметричная (RS256), auth-сервис публикует публичный ключ на `/.well-known/jwks.json`, а остальные сервисы валидируют токен по нему локально, без похода в auth на каждый запрос — точно так же, как этот сервис сейчас проверяет `id_token` Google.
- На Windows `libpq.dll` (и её зависимости — `libssl-3-x64.dll`, `libcrypto-3-x64.dll`, `libintl-9.dll`, `libiconv-2.dll`) линкуются динамически и копируются рядом с `.exe` автоматически при сборке (см. `CMakeLists.txt`) — при ручном переносе бинарника на другую машину не забудьте прихватить и их.
- `redis_client.hpp/.cpp` держит одно TCP-соединение под мьютексом (тот же паттерн, что и `db.hpp`) и не переподключается сам при обрыве — при сетевой аварии между `google-auth` и Redis сервис нужно перезапустить (или доработать клиент реконнектом), само не восстановится. Для реальной нагрузки — то же самое замечание, что и про Postgres выше: один коннект достаточен для демо-масштаба, не для прод-нагрузки.
